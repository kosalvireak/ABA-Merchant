# KHQR Mart Demo (ABA PayWay)

A sample playground for experimenting with **ABA PayWay** QR payments.

The user browses 10 tiny products (100–500 Cambodian Riel), selects one, and
the app immediately shows a dynamic KHQR for that exact price — generated by
the **ABA PayWay QR API** (the [Developer Suite](https://developer.payway.com.kh)).
The customer can scan it with **ABA Mobile** (or any KHQR-member bank app), or
tap the built-in **"Pay with ABA Mobile"** deeplink button. Payment status is
detected live via polling + the PayWay callback webhook.

- **Front-end:** Vue 3 (`<script setup>`, Composition API) + Vite
- **Back-end:** Node.js + Express, ESM
- **Payments:** ABA PayWay QR API — server-side only, HMAC-SHA512 signed
- **Database:** none — products are a static array; transaction status lives in memory

All payment logic lives in the back-end. The front-end never signs requests or
calculates amounts; the server ignores any amount sent by the client — the
price always comes from the server product list.

> Note: this project previously generated KHQR locally with the `bakong-khqr`
> SDK (personal Bakong ID). It has been refactored to PayWay, which adds the
> deeplink flow and a *working* payment-status story.

## Prerequisites

- Node.js 20 or newer
- npm
- A **PayWay merchant account**:
  - **Sandbox (recommended):** register at https://sandbox.payway.com.kh —
    `merchant_id` and `api_key` arrive by email. Sandbox transactions are
    simulated; no real money moves.
  - **Production:** contact `paywaysales@ababank.com`. Your domain must be
    whitelisted by the PayWay integration team (unauthorized calls return
    error `6: wrong domain`). Support: `digitalsupport@ababank.com`.

## Setup

```bash
npm run install:all   # installs server + client dependencies
cp server/.env.example server/.env
# edit server/.env and fill in your PayWay credentials
```

The server refuses to boot while `PAYWAY_MERCHANT_ID` or `PAYWAY_API_KEY` is
missing.

## How to run

```bash
npm run dev
```

Starts both apps together (concurrently):

- Server: http://localhost:3001
- Client: http://localhost:5173  ← open this

## Environment variables (`server/.env`)

| Variable              | Required | Default                                   | Meaning                                                        |
| --------------------- | -------- | ----------------------------------------- | -------------------------------------------------------------- |
| `PORT`                | no       | `3001`                                    | Server port                                                     |
| `CLIENT_ORIGIN`       | no       | `http://localhost:5173`                   | Allowed CORS origin (Vite dev server)                           |
| `PAYWAY_BASE_URL`     | no       | `https://checkout-sandbox.payway.com.kh`  | Sandbox or production gateway base URL                          |
| `PAYWAY_MERCHANT_ID`  | **yes**  | —                                         | Merchant key provided by ABA Bank                               |
| `PAYWAY_API_KEY`      | **yes**  | —                                         | Secret key for HMAC-SHA512 request signing                      |
| `PAYWAY_CALLBACK_URL` | no       | —                                         | Public HTTPS URL for PayWay payment notifications (webhook)     |
| `QR_LIFETIME_MINUTES` | no       | `5`                                       | QR / transaction lifetime (PayWay minimum is 3 minutes)         |
| `PAYWAY_CURRENCY`     | no       | `KHR`                                     | Currency charged on the QR: `KHR` or `USD` (see sandbox note)   |
| `PAYWAY_USD_RATE`     | no       | `4100`                                    | Riel per USD, used to convert prices when `PAYWAY_CURRENCY=USD` |

The webhook needs a **publicly reachable HTTPS URL**. For local testing,
tunnel the server, e.g. `ngrok http 3001`, and set
`PAYWAY_CALLBACK_URL=https://xxxx.ngrok-free.app/api/payments/callback`.
Without it, everything still works — status is detected by polling only.

## API reference

All endpoints return JSON.

| Endpoint                          | Method | Description                                                                                     |
| --------------------------------- | ------ | ----------------------------------------------------------------------------------------------- |
| `/api/health`                     | GET    | `{ "status": "ok" }`                                                                             |
| `/api/products`                   | GET    | The 10-product array                                                                             |
| `/api/products/:id`               | GET    | One product, or 404                                                                              |
| `/api/payments/khqr`              | POST   | Body `{ "productId": "p05" }` → signed `generate-qr` call to PayWay, returns QR + deeplink        |
| `/api/payments/:tranId/status`    | GET    | `{ "status": "PAID" \| "PENDING" \| "UNKNOWN" }` via `check-transaction-2` or the callback store  |
| `/api/payments/callback`          | POST   | PayWay webhook — verifies the notification, then stores the result in memory                     |

Example success response from `POST /api/payments/khqr`:

```json
{
  "productId": "p05",
  "productName": "Potato Chips",
  "amount": 250,
  "currency": "KHR",
  "tranId": "Tkv0n83x2ab9",
  "qrString": "000201010212...",
  "qrImage": "data:image/png;base64,...",
  "abapayDeeplink": "abamobilebank://ababank.com?type=payway&qrcode=...",
  "appStore": "https://itunes.apple.com/...",
  "playStore": "https://play.google.com/...",
  "expiresAt": "2026-11-13T02:12:04.659Z"
}
```

Errors use one consistent shape: `{ "error": { "code": "...", "message": "..." } }`
(400 invalid input / bad callback, 404 unknown product, 500 PayWay failure).

## Testing the flow with ABA Mobile

1. `npm run dev`
2. Open http://localhost:5173 and click a product.
3. Two ways to pay:
   - **Scan** the QR with ABA Mobile → it shows the merchant, amount in KHR
     and receiving account before you confirm.
   - **Tap "Pay with ABA Mobile"** → opens ABA Mobile directly with the
     transaction pre-filled.
4. With `PAYWAY_CALLBACK_URL` configured, the panel flips to **Paid ✓** a few
   seconds after payment; otherwise it flips once the next poll (≤3 s) sees
   the approved transaction.

> **Sandbox caveat:** sandbox transactions are simulated — scanning a sandbox
> QR with the real ABA Mobile app will not complete a payment. In sandbox you
> can exercise the "Paid" path by POSTing a fake webhook and watching it get
> verified:
>
> ```bash
> curl -X POST http://localhost:3001/api/payments/callback \
>   -H 'Content-Type: application/json' \
>   -d '{"tran_id": "<your tranId>", "status": "0"}'
> ```
>
> **KHR on sandbox:** sandbox merchant profiles can ship with KHR disabled.
> If `generate-qr` answers `code 12: Payment currency is not allowed`, either
> enable KHR in the sandbox merchant portal (or ask
> `digitalsupport@ababank.com`), or set `PAYWAY_CURRENCY=USD` to keep testing —
> the server then converts each product's riel price to a 2-decimal USD
> amount (`PAYWAY_USD_RATE`, default 4100) before charging.

## How it works

`server/src/services/payway.service.js` signs every request with
HMAC-SHA512 (base64) over the field values concatenated **in the exact order
the QR API documentation prescribes** (`req_time, merchant_id, tran_id,
amount, items, ..., lifetime, qr_image_template`), then POSTs to
`{PAYWAY_BASE_URL}/api/payment-gateway/v1/payments/generate-qr` with
`currency: "KHR"`, `payment_option: "abapay_khqr"` and the lifetime. PayWay
responds with the QR string, a ready-made base64 PNG and the ABA Mobile
deeplink. Payment status uses `check-transaction-2` (status codes: `0`
APPROVED → PAID, `2` PENDING, others UNKNOWN; `6` = transaction not found →
treated as PENDING).

## Tests

```bash
npm test   # runs vitest + supertest in server/ (PayWay is mocked, no network)
```

Covers: product list shape, hash signing order, request assembly
(currency/options/amount as server-side values), PayWay rejection mapping,
status-code mapping, the callback → status store flow.

## Known limitations

- No database: transaction status lives in memory and is lost on restart
  (the server then simply re-asks PayWay for the truth).
- Single product per QR — no cart or totals.
- Currency is KHR only. USD, WeChat/Alipay QRs are a config-level change
  (`currency` + `payment_option`) but out of scope here.
- Sandbox QRs can't be paid with a real bank app (simulated money).
- The webhook verification trusts `check-transaction`, not the raw payload.
- Demo only: no auth, no HTTPS termination, a light per-IP rate limit only.
